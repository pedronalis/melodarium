# Qt 6.10 — esqueleto de build e ponte C++ ↔ QML

Verificado nesta máquina: Fedora 43, Qt 6.10.3 (`qt6-qtbase-devel`, `qt6-qtdeclarative-devel` etc.),
gcc 15.3.1, cmake 3.31.11, ninja 1.13.1, mpv 0.40.0, TagLib 1.13.1, mpvqt-devel 1.0.1.
Todo trecho de código abaixo foi **compilado e executado de verdade** num projeto de teste em
`/tmp/.../scratchpad/qttest` (não é memória de treino) — as armadilhas descritas são falhas reais
que aconteceram nesse teste, não hipóteses.

`qt5compat` (o pacote, não o módulo `Qt6::Core5Compat`) **NÃO está instalado** nesta máquina. Não é
necessário para nada do que está aqui; se algum plano futuro precisar de `Qt.labs` legado, verificar
antes de assumir que existe.

## 1. CMakeLists.txt mínimo que compila

Estrutura de pastas recomendada (testada): `melodia/CMakeLists.txt` + `melodia/src/` com
`main.cpp`, `Main.qml`, `library.h/.cpp` (singleton), `tracklistmodel.h/.cpp` (modelo).

```cmake
cmake_minimum_required(VERSION 3.21)
project(melodia LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_AUTOMOC ON)

find_package(Qt6 REQUIRED COMPONENTS Core Quick Sql Concurrent Network)
qt_standard_project_setup(REQUIRES 6.5)

qt_add_executable(appmelodia
    src/main.cpp
    src/tracklistmodel.h
    src/tracklistmodel.cpp
    src/library.h
    src/library.cpp
)

qt_add_qml_module(appmelodia
    URI Melodia.App
    VERSION 1.0
    QML_FILES
        src/Main.qml
    SOURCES
        src/tracklistmodel.h
        src/tracklistmodel.cpp
)

# ARMADILHA (verificada): sem isto o build QUEBRA. Ver seção "Armadilhas".
target_include_directories(appmelodia PRIVATE src)

target_link_libraries(appmelodia PRIVATE
    Qt6::Core Qt6::Quick Qt6::Sql Qt6::Concurrent Qt6::Network
)

# libmpv e TagLib via pkg-config — nenhum dos dois exporta Config.cmake de Qt

pkg_check_modules(TAGLIB REQUIRED IMPORTED_TARGET taglib)
target_link_libraries(appmelodia PRIVATE PkgConfig::MPV PkgConfig::TAGLIB)
```

Build e execução (comandos literais testados):

```bash

cmake --build build
QT_QPA_PLATFORM=offscreen ./build/appmelodia   # offscreen só para CI/teste sem tela
./build/appmelodia                              # execução normal no Hyprland/Wayland
```

### Armadilha 1 (grave, quebra o build): include directory do `src/`

`qt_add_qml_module` gera `appmelodia_qmltyperegistrations.cpp` com
`#if __has_include(<tracklistmodel.h>) #include <tracklistmodel.h> #endif` — inclui o header pelo
**nome puro** em `<>`, não pelo caminho relativo. Sem `src/` no include path do alvo, o
`__has_include` falha em silêncio e o que sobra é uma cascata de ~15 erros de template
("was not declared in this scope") que não apontam pra causa real. Reproduzido e confirmado
nesta sessão; fix é a linha `target_include_directories(appmelodia PRIVATE src)` acima.

### Armadilha 2: `pkg-config --modversion mpv` mente sobre a versão do mpv

`pkg-config --modversion mpv` devolve **2.5.0** nesta máquina, não "0.40.0". Isso é a versão da
**API cliente do libmpv** (o `.pc` é gerado pelo próprio mpv com esse número), não a versão do
programa mpv. Não use essa string para decidir "quais funções existem" — as assinaturas em
`mpv/client.h` (ex.: `mpv_create`, `mpv_observe_property`, `mpv_set_wakeup_callback`) são as mesmas
verificadas abaixo, e batem com o mpv 0.40 instalado.

### `mpvqt-devel` existe mas não é o caminho certo para este projeto

Tem um `find_package(MpvQt)` funcional (`/usr/lib64/cmake/MpvQt/`, alvo `MpvQt::MpvQt`), mas a
classe que ele oferece para tocar mídia, `MpvAbstractItem`, herda de `QQuickFramebufferObject` —
feita para **renderizar vídeo dentro de um item QML**. Melodia é áudio (FLAC/gapless/ReplayGain,
sem vídeo); usar essa classe carregaria máquina de renderização OpenGL à toa. Recomendação: libmpv
puro via pkg-config (seção "Motor de áudio" abaixo), sem dependência de `Qt6::Quick` no motor.

## 2. main.cpp

```cpp
// src/main.cpp
#include <QGuiApplication>
#include <QQmlApplicationEngine>

int main(int argc, char *argv[])
{
    QGuiApplication app(argc, argv);

    QQmlApplicationEngine engine;
    QObject::connect(&engine, &QQmlApplicationEngine::objectCreationFailed,
                      &app, []() { QCoreApplication::exit(-1); },
                      Qt::QueuedConnection);

    // Carrega pelo URI do módulo (qt_add_qml_module), não por caminho de arquivo.
    engine.loadFromModule("Melodia.App", "Main");

    return app.exec();
}
```

`loadFromModule(uri, typeName)` é o padrão Qt 6.5+ (testado em 6.10.3) — resolve
`Melodia.App/Main` pelo qmldir gerado, em vez do antigo `engine.load(QUrl("qrc:/..."))`.

## 3. Registro de tipos: qual macro para cada caso

Todas verificadas em `/usr/include/qt6/QtQmlIntegration/qqmlintegration.h`:

| Caso do projeto                                       | Macro                                                          | Efeito                                                    |
| ----------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------- |
| Motor de áudio (instância única, controlada pelo app) | `QML_ELEMENT` + `QML_SINGLETON`                                | QML acessa por **nome do tipo**, nunca instancia com `{}` |
| Biblioteca/banco (idem, singleton)                    | `QML_ELEMENT` + `QML_SINGLETON`                                | idem                                                      |
| Modelo de lista (TrackListModel, um por tela)         | `QML_ELEMENT`                                                  | QML instancia normalmente com `TrackListModel { }`        |
| Enum usado em QML (roles de filtro, etc.)             | `Q_ENUM(NomeDoEnum)` dentro da classe que já tem `QML_ELEMENT` | expõe `Tipo.Valor` para o QML                             |

```cpp
// src/library.h — singleton
#pragma once
#include <QObject>
#include <QtQmlIntegration/qqmlintegration.h>

class Library : public QObject
{
    Q_OBJECT
    QML_ELEMENT
    QML_SINGLETON
public:
    explicit Library(QObject *parent = nullptr);
    Q_INVOKABLE int trackCount() const;
};
```

```qml
// uso em QML — SEM declarar instância:
import Melodia.App
Item {
    Component.onCompleted: console.log(Library.trackCount())
}
```

### Armadilha 3 (confirmada por erro real): `Singleton { }` não instancia

`Library { id: lib }` em QML para um tipo `QML_SINGLETON` dá `Element is not creatable` (mensagem
exata capturada no teste). Por design: singleton se referencia pelo **nome do tipo**, nunca com
chaves — vai morder na primeira vez que declararem o motor de áudio como um Item comum.

### Armadilha 4 (confirmada): enum sem `Q_ENUM` não aparece no QML

`enum Roles { TitleRole = Qt::UserRole+1, ... }` numa classe `QML_ELEMENT` não fica visível como
`TrackListModel.TitleRole` em QML sem `Q_ENUM(Roles)` logo depois. Sem isso resolve para
`undefined` em silêncio (só um warning em runtime, sem erro de compilação QML).

## 4. Modelos de lista

```cpp
// src/tracklistmodel.h
#pragma once
#include <QAbstractListModel>
#include <QtQmlIntegration/qqmlintegration.h>

struct TrackItem { QString title; QString artist; QString album; int durationMs = 0; bool isPlaying = false; };

class TrackListModel : public QAbstractListModel
{
    Q_OBJECT
    QML_ELEMENT
public:
    enum Roles { TitleRole = Qt::UserRole + 1, ArtistRole, AlbumRole, DurationRole, IsPlayingRole };
    Q_ENUM(Roles)

    explicit TrackListModel(QObject *parent = nullptr);
    int rowCount(const QModelIndex &parent = QModelIndex()) const override;
    QVariant data(const QModelIndex &index, int role) const override;
    QHash<int, QByteArray> roleNames() const override;

    void addTrack(const TrackItem &t);      // usa beginInsertRows — 1 faixa nova (scan incremental)
    void resetTracks(QList<TrackItem> ts);  // usa beginResetModel — recarga completa (troca de coleção)

private:
    QList<TrackItem> m_items;
};
```

```cpp
// src/tracklistmodel.cpp
#include "tracklistmodel.h"

TrackListModel::TrackListModel(QObject *parent) : QAbstractListModel(parent) {}

int TrackListModel::rowCount(const QModelIndex &parent) const
{
    return parent.isValid() ? 0 : m_items.size();
}

QVariant TrackListModel::data(const QModelIndex &index, int role) const
{
    if (!index.isValid() || index.row() >= m_items.size()) return {};
    const auto &t = m_items.at(index.row());
    switch (role) {
    case TitleRole: return t.title;
    case ArtistRole: return t.artist;
    case AlbumRole: return t.album;
    case DurationRole: return t.durationMs;
    case IsPlayingRole: return t.isPlaying;
    }
    return {};
}

QHash<int, QByteArray> TrackListModel::roleNames() const
{
    return { {TitleRole, "title"}, {ArtistRole, "artist"}, {AlbumRole, "album"},
             {DurationRole, "duration"}, {IsPlayingRole, "isPlaying"} };
}

void TrackListModel::addTrack(const TrackItem &t)
{
    beginInsertRows(QModelIndex(), m_items.size(), m_items.size());
    m_items.append(t);
    endInsertRows();
}

void TrackListModel::resetTracks(QList<TrackItem> ts)
{
    beginResetModel();
    m_items = std::move(ts);
    endResetModel();
}
```

**Quando usar cada um:** insert/remove quando sabe exatamente quais linhas mudaram (faixa nova
achada no scan, tocar/pausar) — a view anima e não perde scroll/seleção. Reset quando o conteúdo
inteiro trocou sem relação com o anterior (trocar de coleção) — mais barato de escrever, mas reseta
seleção e scroll.

### Filtro/busca: `QSortFilterProxyModel` a partir do QML

Confirmado no header (`qsortfilterproxymodel.h`): a classe em si **não** tem `QML_ELEMENT` — não dá
para usar `SortFilterProxyModel { }` puro em QML no Qt 6.10. A rota que funciona (testada, o filtro
funcionou de verdade — `rowCount` caiu para o esperado após `setFilterFixedString`) é subclassar:

```cpp
// src/trackfiltermodel.h
#pragma once
#include <QSortFilterProxyModel>
#include <QtQmlIntegration/qqmlintegration.h>

class TrackFilterModel : public QSortFilterProxyModel
{
    Q_OBJECT
    QML_ELEMENT
public:
    explicit TrackFilterModel(QObject *parent = nullptr) : QSortFilterProxyModel(parent) {
        setFilterCaseSensitivity(Qt::CaseInsensitive);
    }
};
```

```qml
TrackListModel { id: model }
TrackFilterModel {
    id: filterModel
    sourceModel: model               // Q_PROPERTY herdado, funciona direto do QML
    filterRole: TrackListModel.TitleRole
}
// filterModel.setFilterFixedString("busca do usuário")
```

`sourceModel` e `filterRole` são `Q_PROPERTY` herdados da base — o meta-object system do Qt
propaga propriedades de classe-base para a subclasse registrada, não precisa redeclarar nada, só o
`QML_ELEMENT`. Existe um `QQmlSortFilterProxyModel` dentro de `QtQmlModels`, mas é **privado**
(`private/qqmlsortfilterproxymodel_p.h`) — não é API pública, não usar.

## 5. Threads — o ponto de crash mais provável

### Motor de áudio: libmpv puro, não `MpvAbstractItem`

Todas as assinaturas abaixo conferidas em `/usr/include/mpv/client.h` (mpv 0.40, API cliente 2.5.0):

```cpp
mpv_handle *mpv_create(void);
int  mpv_initialize(mpv_handle *ctx);
void mpv_set_wakeup_callback(mpv_handle *ctx, void (*cb)(void *d), void *d);
int  mpv_command(mpv_handle *ctx, const char **args);         // NULL-terminated
int  mpv_set_property_string(mpv_handle *ctx, const char *name, const char *data);
int  mpv_observe_property(mpv_handle *mpv, uint64_t reply_userdata, const char *name, mpv_format format);
mpv_event *mpv_wait_event(mpv_handle *ctx, double timeout);
void mpv_terminate_destroy(mpv_handle *ctx);
```

Padrão Qt+libmpv (evita polling): `mpv_set_wakeup_callback` roda numa thread do mpv, então o callback
só deve fazer uma coisa segura — acordar a thread Qt, via
`QMetaObject::invokeMethod(engineObj, "processMpvEvents", Qt::QueuedConnection)`. Dentro de
`processMpvEvents` (já na thread Qt), chamar `mpv_wait_event(ctx, 0)` em loop até `MPV_EVENT_NONE`.

### Scan de biblioteca (5000 arquivos, TagLib) sem travar a UI

**Recomendação: `QThread` + objeto worker (`moveToThread`), não `QtConcurrent::run`.** O scan precisa
de progresso incremental, cancelamento limpo, e uma `QSqlDatabase` isolada viva por toda a vida do
scan — `QtConcurrent::run` roda no `QThreadPool` global, ótimo para "uma função, um resultado", mas
sem lugar natural para manter conexão nem checar flag de cancelamento.

```cpp
// scanner.h
class LibraryScanner : public QObject {
    Q_OBJECT
public slots:
    void run(const QString &rootPath);
signals:
    void progress(int done, int total);
    void trackFound(const TrackItem &t);
    void finished();
};

// scanner.cpp — roda inteiro na thread do worker
void LibraryScanner::run(const QString &rootPath)
{
    auto db = QSqlDatabase::addDatabase("QSQLITE", "scanner-conn"); // ver ARMADILHA 5 abaixo
    db.setDatabaseName(dbPath);
    db.open();
    // ... enumerar arquivos, ler tags com TagLib::FileRef, inserir no SQLite ...
    for (int i = 0; i < files.size(); ++i) {
        // ... TagLib::FileRef f(files[i].toUtf8().constData()); ...
        if (i % 20 == 0) emit progress(i, files.size()); // não emitir a cada arquivo — satura a fila de eventos
    }
    db.close();
    QSqlDatabase::removeDatabase("scanner-conn");
    emit finished();
}

// no lado da UI/main thread:
QThread *thread = new QThread;
LibraryScanner *scanner = new LibraryScanner;
scanner->moveToThread(thread);
connect(thread, &QThread::started, scanner, [=]{ scanner->run(libraryPath); });
connect(scanner, &LibraryScanner::finished, thread, &QThread::quit);
connect(thread, &QThread::finished, scanner, &QObject::deleteLater);
connect(thread, &QThread::finished, thread, &QObject::deleteLater);
thread->start();
```

`progress`/`trackFound`/`finished` cruzam de thread do worker para a UI automaticamente como
`Qt::QueuedConnection` (padrão quando emissor/receptor vivem em threads diferentes) — o slot roda no
event loop da UI, seguro para tocar em modelos QML.

### Regra do SQLite com threads (verificada com teste real, thread + QSqlDatabase)

**Uma `QSqlDatabase` por thread, com nome de conexão próprio.** Testei de verdade: thread principal
com uma conexão, worker com outra, ambas inserindo no mesmo `.db` com `PRAGMA journal_mode=WAL` —
sem corromper nada. `QSqlDatabase::database()` sem argumento é por-processo, não por-thread; passar
`QSqlQuery`/`QSqlDatabase` entre threads ou compartilhar nome de conexão é comportamento indefinido
(a doc do Qt é explícita: conexão só pode ser usada pela thread que a criou).

**Vale usar WAL:** sim — confirmado retornando `"wal"` no teste — permite escritor (scanner) e
leitor (UI) simultâneos sem bloqueio; sem WAL o modo padrão bloqueia leitores durante escrita.

### Armadilha 5 (confirmada, warning real capturado): ordem de destruição do `QSqlDatabase`

```
QSqlDatabasePrivate::removeDatabase: connection 'worker-conn' is still in use, all queries will cease to work.
```

Apareceu porque a variável local `db` (handle/referência à conexão) ainda estava viva no escopo
quando `removeDatabase("worker-conn")` foi chamado em seguida — `removeDatabase` exige que **todas**
as cópias de `QSqlDatabase` daquele nome já tenham saído de escopo. Fix: colocar `db` num bloco `{ }`
que termina antes do `removeDatabase`, ou chamar `removeDatabase` de fora, depois que `db` já não existe.

## 7. Desenvolver a tela sem recompilar C++

**Achado (confirmado por erro real):** com `qt_add_qml_module` direto sobre `qt_add_executable`, os
tipos C++ ficam **estaticamente linkados dentro do binário do app** — não existe `.so` de plugin
separado. Apontei a ferramenta standalone `/usr/lib64/qt6/bin/qml -I build arquivo.qml` para um QML
que usa `TrackFilterModel` e o erro foi `"TrackFilterModel is not a type"`: o `qmldir` foi
encontrado, mas o tipo C++ não, porque o plugin que o registraria não existe como artefato separado.
**A ferramenta `qml` não serve para hot-reload aqui**, a menos que se separe numa lib própria —
complexidade desnecessária nesta fase.

**Rota recomendada** (APIs confirmadas existir, ciclo completo não testado em janela interativa): um
"modo dev" no `main.cpp`, ligado por variável de ambiente, que carrega o QML direto do disco e
observa o arquivo:

```cpp
if (qEnvironmentVariableIsSet("MELODIA_DEV_QML")) {
    QString path = qEnvironmentVariable("MELODIA_DEV_QML"); // ex: /home/pedro/dev/.../src/Main.qml
    auto *watcher = new QFileSystemWatcher(&engine);
    watcher->addPath(path);
    auto reload = [&engine, path]() {
        engine.clearComponentCache();          // QQmlEngine::clearComponentCache(), confirmado no header
        engine.load(QUrl::fromLocalFile(path));
    };
    QObject::connect(watcher, &QFileSystemWatcher::fileChanged, &engine, reload);
    reload();
} else {
    engine.loadFromModule("Melodia.App", "Main");
}
```

Isso dá "salvou o `.qml`, a janela já mostrou" sem `cmake --build` — os tipos C++ continuam
disponíveis porque já estão linkados no binário, só o texto QML é relido do disco. Autocomplete de
editor: `qmlls` já está instalado em `/usr/bin/qmlls` (confirmado).

### Armadilha 6 (grande, confirmada): saída de `qDebug`/`qWarning`/`console.log` some por padrão nesta máquina

A descoberta mais cara da sessão. Fedora instala `/usr/share/qt6/qtlogging.ini` com `*.debug=false`
— desliga **globalmente**, para qualquer app Qt6 na máquina, mensagens de nível debug, inclusive
`console.log()` do QML (categoria `qml`, nível debug). Além disso o handler padrão do Qt manda
`qDebug`/`qWarning` para o `journald`, não para o stderr do terminal, quando detecta que não está
anexado a um terminal interativo — exatamente o caso de rodar via shell/agente. Resultado: um
`qWarning()` no meio do código não aparece em lugar nenhum por padrão, nem dá erro.

Resolvido com duas variáveis de ambiente, **as duas precisam estar juntas**:

```bash
QT_LOGGING_RULES="*.debug=true" QT_FORCE_STDERR_LOGGING=1 ./build/appmelodia
```

- `QT_LOGGING_RULES="*.debug=true"` religa mensagens de nível debug (sem isso, mesmo forçando
  stderr, debug/console.log não é gerado).
- `QT_FORCE_STDERR_LOGGING=1` (ou `QT_LOGGING_TO_CONSOLE=1`, também testado) força destino stderr.

Sem as duas, qualquer sessão de debug futura vai parecer "não fez nada" quando na verdade fez — a
mensagem foi para o journal. Para conferir: `journalctl -n 50 --no-pager | grep <nome-do-executavel>`.
